01O Marco 3 inteiro: cadastro e edição

O Marco 2 mostrava os dados. O Marco 3 permite criar e editar tarefas e projetos. Este guia cobre os oito itens da equipe, da #16 à #23, e mostra como eles se conectam no código.

Uma diferença que vale saber explicar

A #17 pede reaproveitar o formulário de tarefa no cadastro e na edição. O componente FormularioTarefa foi preparado para isso, mas, nesta base, a nova tarefa mantém formulário próprio e a edição usa o componente. Ambos compartilham os auxiliares de validação. Nos projetos, cadastro e edição usam o mesmo FormularioProjeto.

A #19 ainda aparece aberta no GitHub na consulta de 22/10/2026, embora o arquivo de edição já exista em main. Explicar código existente e encerrar uma issue são ações diferentes.

Um arquivo Svelte costuma juntar três partes:

  • <script lang="ts">: TypeScript, com dados e funções.
  • Marcação HTML/Svelte: os campos, textos e botões que aparecem.
  • <style>: CSS, que organiza a aparência da página.

Os exemplos deste guia são recortes para estudar os conceitos; os arquivos do projeto são a referência para o código completo.

03Como o endereço encontra a página?

src/routes/tarefas/nova/+page.svelte
                    ↓
               /tarefas/nova

src/routes/tarefas/[id]/+page.svelte
                    ↓
           /tarefas/2, /tarefas/abc...

nova é uma parte fixa do endereço. [id] é uma parte variável. O SvelteKit escolhe a rota fixa antes da variável; por isso, abrir /tarefas/nova deve mostrar o cadastro, sem tentar buscar uma tarefa cujo ID seja “nova”.

E o projeto já selecionado?

O link do projeto leva uma informação extra depois do ponto de interrogação:

/tarefas/nova?projetoId=3

/tarefas/nova escolhe a página. projetoId=3 sugere qual projeto selecionar. Isso é um parâmetro de consulta, também chamado de query parameter.

import { page } from '$app/state';

page.url.searchParams.get('projetoId'); // "3"

page vem do SvelteKit e informa a URL atual. Ele não é o roteador. Também não confundimos a consulta acima com page.params.id, que lê a parte [id] de uma rota dinâmica.

Antes de selecionar, o código confere se esse ID existe nos projetos que vieram da API. Se alguém escrever um ID inválido na URL, o formulário deve orientar a pessoa a escolher um projeto válido.

Por que usar $derived e $effect aqui?

O SvelteKit pode manter a mesma página aberta quando só a consulta muda. Por isso, observar a sugestão da URL permite atualizar o projeto ao ir de ?projetoId=1 para ?projetoId=2. O efeito observa a sugestão e os projetos carregados; ele não deve observar o campo que a pessoa edita, para não desfazer a escolha manual dela.

As quatro páginas novas do marco

URL no navegadorPasta dentro de src/routes
/tarefas/novatarefas/nova/+page.svelte
/tarefas/2/editartarefas/[id]/editar/+page.svelte

:id é uma forma de descrever o endereço no enunciado. A pasta do SvelteKit se chama [id]; no navegador você usa um valor real, como 2. A regra de rota fixa também protege /projetos/novo.

04Como o formulário guarda o que eu digito?

Os dados enviados são: projetoId, titulo, descricao, status, prioridade, responsavel e prazo. Os nomes precisam respeitar o contrato que a API usa.

NovaTarefa: o formato dos dados

export type NovaTarefa = Omit<Tarefa, 'id'>;

Omit significa “usar os campos de Tarefa, retirando id”. O usuário não inventa o ID. O json-server o gera quando grava a tarefa.

O TypeScript ajuda a detectar nomes e tipos errados enquanto programamos. Ele não substitui as verificações do formulário nem a validação de um servidor real.

$state: um valor que atualiza a tela

let titulo = $state('');

Esse recorte começa com um título vazio. Quando o estado muda, o Svelte atualiza a parte da tela que depende dele. Na página completa, os campos podem estar agrupados em um objeto.

bind:value: ligar o campo ao estado

<label for="titulo">Título</label>
<input id="titulo" bind:value={titulo} required />

Ao digitar no campo, titulo recebe o valor. Se o código mudar titulo, o campo também muda. O label dá nome ao campo; o for aponta para seu id. required pede ao navegador que não envie esse campo vazio.

onMount: buscar as opções depois de abrir

listarProjetos() fornece as opções do seletor. onMount executa a busca quando a página é montada no navegador. Enquanto a resposta não chega, mostramos carregamento; se falhar, mostramos uma mensagem e permitimos tentar de novo.

Duas ideias diferentes: onMount inicia essa busca. O efeito acompanha a sugestão de projeto da URL. Um não substitui automaticamente o outro.

05Issue #17: o componente de formulário

Um componente é um pedaço da interface com seus próprios campos e comportamento. A página decide qual registro editar e o que fazer ao salvar; o formulário organiza a digitação.

Props são as entradas do componente

Em FormularioTarefa.svelte, $props() recebe estas entradas:

PropPara que serve
valorInicialDados de partida. Um objeto vazio serve como base de cadastro; uma tarefa existente preenche a edição.
textoEnvioTexto do botão, como “Salvar alterações”.
enviandoInforma que a gravação está em andamento.
erroMensagem da falha de gravação, passada pela página.
onenviarFunção que recebe os campos preenchidos quando o formulário é enviado.
<FormularioTarefa
  valorInicial={tarefa}
  textoEnvio="Salvar alterações"
  {enviando}
  erro={erroEnvio}
  onenviar={salvar}
/>

Esse recorte é o uso real na página de edição. onenviar={salvar} entrega uma função. Quando o componente chama onenviar(dados), a função salvar da página é executada. Isso é um callback.

Por que copiar os valores iniciais?

O componente começa com campos vazios e valores padrão e aplica valorInicial por cima. Usa $state para guardar a edição local e untrack na leitura inicial. Assim, a digitação é controlada pelo próprio formulário; receber os dados iniciais não significa alterar diretamente o registro original da API.

O seletor busca os projetos com listarProjetos() e repete as opções usando {#each}. O valor de cada opção é o ID do projeto, enquanto o texto mostrado é seu nome.

Conferência entre pedido e código: o componente permite receber dados diferentes, mas a tela /tarefas/nova ainda não o utiliza. Unificar as duas telas é uma melhoria possível; não apresente essa unificação como já feita. A descrição é obrigatória no cadastro e opcional no componente usado na edição.

Como chegar: abra src/lib/componentes/FormularioTarefa.svelte, procure type Props, $props(), bind:value e onenviar. Depois compare com a chamada na página de edição.

06O que acontece ao clicar em Salvar?

Um formulário trata seu envio com uma função. Ela impede o envio tradicional do navegador, prepara os dados e aguarda a API.

OperaçãoO que ela faz no projeto
GET /projetosLê os projetos para o seletor.
POST /tarefasEnvia os dados para criar uma tarefa.
goto('/')Abre a página da lista depois da confirmação de criação.

Recorte do formato de uma requisição de criação:

fetch('http://localhost:3000/tarefas', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify(dados)
});
  • method: 'POST' informa que queremos criar um registro.
  • Content-Type informa que o corpo usa JSON.
  • JSON.stringify(dados) transforma o objeto TypeScript/JavaScript em texto JSON para enviar.
  • criarTarefa(dados) reúne essa conversa com a API em uma função que a página chama.

Por que async e await?

const tarefaCriada = await criarTarefa(dados);
await goto('/');

A API leva algum tempo para responder. await espera o resultado dentro de uma função async. Só depois de criar a tarefa a navegação é iniciada.

A lista fica em /, e não em /tarefas. Ao voltar para ela, a busca da lista carrega os registros, incluindo a tarefa nova.

E se der erro?

try tenta a operação e catch trata uma falha. Se a gravação falhar, os campos continuam preenchidos para a pessoa tentar novamente. Durante o envio, o botão fica desabilitado para evitar pedidos repetidos.

Se a API já confirmou a criação, uma falha ao navegar não deve habilitar uma segunda gravação da mesma tarefa. A página reconhece o sucesso e permite voltar à lista. O onDestroy também marca quando você saiu desta tela, para uma resposta atrasada não forçar a navegação depois disso.

07A API agora também escreve

Antes, o módulo da API sabia ler: listar tarefas, buscar uma tarefa e carregar projetos. A #16 acrescenta quatro funções. A página passa os dados para elas; cada função monta a requisição correta e devolve a resposta da API.

Função e retornoPedido enviado
criarTarefa(dados: NovaTarefa): Promise<Tarefa>POST /tarefas. Envia os campos da nova tarefa e recebe a tarefa criada, com ID.
atualizarTarefa(id: string, dados: AtualizacaoTarefa): Promise<Tarefa>PATCH /tarefas/ID. Envia os campos que devem mudar e recebe a tarefa atualizada.
criarProjeto(dados: NovoProjeto): Promise<Projeto>POST /projetos. Envia os campos do novo projeto e recebe o projeto criado, com ID.
atualizarProjeto(id: string, dados: AtualizacaoProjeto): Promise<Projeto>PATCH /projetos/ID. Envia os campos que devem mudar e recebe o projeto atualizado.

Essas assinaturas são um mapa: o que está entre parênteses é a entrada; o que vem depois de : é o tipo do retorno.

Omit, Partial e Promise<T>

export type NovaTarefa = Omit<Tarefa, 'id'>;
export type AtualizacaoTarefa = Partial<NovaTarefa>;

export type NovoProjeto = Omit<Projeto, 'id'>;
export type AtualizacaoProjeto = Partial<NovoProjeto>;
  • Omit retira um campo de um tipo. Na criação, retiramos id porque a API o gera.
  • Partial torna os campos opcionais. Podemos atualizar só status, sem repetir o restante da tarefa.
  • Promise<Tarefa> representa um resultado futuro. Depois do await, obtemos uma Tarefa se o pedido tiver sucesso. Uma falha precisa ser tratada.

São tipos derivados: os campos e os nomes do contrato original de Tarefa e Projeto continuam os mesmos. A tipagem auxilia o desenvolvimento, mas não valida sozinha os dados recebidos pela rede.

Quando usar GET, POST, PATCH ou PUT?

MétodoIdeia e uso aqui
GETLer. Exemplo: carregar os projetos do seletor.
POSTCriar. Aqui, enviamos um novo registro à coleção /tarefas ou /projetos.
PATCHAlterar parte de um registro existente. No json-server deste projeto, enviamos um objeto JSON com os campos que devem mudar.
PUTSubstituir a representação completa de um registro. Não é o método escolhido por estas funções, que aceitam atualizações parciais.

O formato aceito por um PATCH depende da API. Aqui usamos o contrato do json-server; isso não significa que todo servidor aceite o mesmo corpo JSON. A distinção entre alteração parcial e substituição é descrita na especificação de PATCH.

Atualizar uma tarefa: ID na URL, mudanças no corpo

const tarefa = await atualizarTarefa('2', {
  status: 'em-andamento'
});

O '2' identifica qual tarefa queremos alterar. O objeto informa o que deve mudar. O pedido corresponde a PATCH /tarefas/2 com o corpo { "status": "em-andamento" }. Os demais campos são preservados pelo json-server.

A função usa encodeURIComponent(id) ao montar o endereço. Assim, caracteres especiais do ID não viram separadores de caminho ou de consulta da URL por acidente. O ID é recebido separadamente e não é um campo de AtualizacaoTarefa.

Criar e depois atualizar um projeto

const projeto = await criarProjeto({
  nome: 'Estudo de Svelte',
  descricao: 'Exercícios da equipe',
  disciplina: 'Desenvolvimento Front-end',
  criadoEm: '2026-10-21'
});

const atualizado = await atualizarProjeto(projeto.id, {
  descricao: 'Exercícios e revisão da equipe'
});

Quem chama criarProjeto fornece criadoEm, junto com os outros campos exigidos. A função de serviço não inventa essa data; a API gera somente o ID. A atualização do exemplo altera apenas a descrição.

Por que existe o auxiliar requisitar?

As funções precisam fazer tarefas em comum: chamar fetch, verificar a resposta e ler o JSON. O auxiliar centraliza esses passos para não repeti-los em cada operação.

async function requisitar<T>(
  caminho: string,
  opcoes?: RequestInit
): Promise<T>

RequestInit é o tipo das opções aceitas pelo fetch, como method, headers e body. O ? torna esse argumento opcional. As leituras podem chamar apenas com o caminho; as escritas passam suas opções.

return requisitar<Tarefa>(
  `/tarefas/${encodeURIComponent(id)}`,
  {
    method: 'PATCH',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(dados)
  }
);

O T indica o tipo de resposta esperado por quem chama. Em requisitar<Tarefa>, esperamos uma tarefa; em requisitar<Projeto>, esperamos um projeto.

Como ErroApi ajuda?

Se a resposta HTTP não indicar sucesso, o auxiliar lança ErroApi, guardando o código em status. Uma tela pode distinguir, por exemplo, um registro não encontrado (404) de outra falha.

try {
  await atualizarTarefa('2', { prioridade: 'alta' });
} catch (erro) {
  if (erro instanceof ErroApi && erro.status === 404) {
    // Mostrar que a tarefa não foi encontrada.
  } else {
    // Mostrar que não foi possível salvar a alteração.
  }
}

Uma falha de conexão pode ocorrer antes de existir resposta HTTP. Nesse caso, o erro original do fetch também chega ao catch; não presumimos que todo erro seja um ErroApi.

Como chegar a esta parte no código: abra src/lib/servicos/api.ts e procure as quatro funções da tabela. Depois abra src/tipos.ts para ver seus tipos de entrada. Na tela de nova tarefa, procure a chamada de criarTarefa: ela é a ligação entre as issues #18 e #16.

08Issue #19: editar uma tarefa existente

Cadastro começa vazio e cria um registro. Edição começa com um registro já salvo e altera esse mesmo registro. Em /tarefas/2/editar, o ID 2 escolhe qual tarefa carregar.

  1. Ler page.params.id.
  2. Chamar buscarTarefa(id), que faz GET.
  3. Mostrar carregamento ou erro; quando chegar a tarefa, preencher FormularioTarefa.
  4. Receber os dados pelo callback salvar.
  5. Aguardar atualizarTarefa(tarefa.id, dados), que faz PATCH, e navegar para o detalhe.
await atualizarTarefa(tarefa.id, dados);
await goto(`/tarefas/${tarefa.id}`);

Por que há um $effect?

A página observa o ID da URL. Se ele mudar, busca o novo registro. O efeito usa uma variável ativo e uma função de limpeza: uma resposta antiga não deve substituir os dados de outra tarefa depois da troca de rota.

ErroApi com status 404 vira “Tarefa não encontrada”. Outras falhas de busca recebem uma mensagem de carregamento malsucedido. A falha ao salvar usa outro estado, erroEnvio, e mantém o formulário disponível para correção ou nova tentativa.

Quem faz o quê?

O componente guarda os campos e valida. A página chama a API e controla enviando. O módulo da API monta o pedido HTTP. Essa separação permite estudar cada responsabilidade sem misturar tudo em uma função.

Como chegar: abra src/routes/tarefas/[id]/editar/+page.svelte. Procure buscarTarefa, valorInicial={tarefa} e atualizarTarefa. Ao demonstrar, altere um campo, salve e confira o mesmo ID no detalhe.

09Validar antes de enviar

A #20 trabalha em duas frentes: conferir o que a pessoa preencheu e impedir outro envio enquanto o primeiro está em andamento. Para isso, aproveitamos a validação do navegador e o auxiliar de acessibilidade que já veio do grupo.

Por que required sozinho não cobre tudo?

''      // vazio
'   '   // tem caracteres, mas só espaços
'Svelte' // tem texto

Em um campo de texto, required bloqueia o valor vazio. Um texto formado apenas por espaços pode passar por essa regra. A função textoObrigatorioValido acrescenta a conferência que faltava:

export function textoObrigatorioValido(valor: string): boolean {
  return valor.trim().length > 0;
}

trim() obtém o texto sem espaços em branco nas pontas. Se nada sobrar, o resultado tem tamanho zero e a função retorna false. Ela usa esse resultado para conferir o preenchimento; não modifica por conta própria o texto digitado.

Como essa regra chega ao formulário?

validarObrigatorios é uma action do Svelte: uma função ligada a um elemento por use:. Ela recebe o formulário quando ele é montado no navegador e acompanha os campos de texto.

<form
  onsubmit={aoEnviar}
  use:validarObrigatorios
  use:acessibilidadeFormulario
>
  ...
</form>

A nova action examina somente input type="text" e textarea com required. O seletor de projeto e o prazo continuam com suas regras nativas. A descrição é obrigatória no cadastro de nova tarefa; no formulário de edição, continua opcional conforme a entrega do colega.

setCustomValidity: adicionar uma regra ao navegador

campo.setCustomValidity(
  'Preencha este campo com texto, sem usar somente espaços.'
);

// Depois que essa regra for atendida:
campo.setCustomValidity('');

Uma mensagem não vazia marca um erro personalizado. Passar '' limpa esse erro, permitindo ao navegador avaliar as outras regras. Não significa declarar que qualquer valor é válido.

O código deixa o valor realmente vazio para required tratar. A regra personalizada cuida do valor que contém caracteres, mas fica vazio depois de trim(). O formulário mantém a validação nativa do HTML, sem novalidate.

Por que o erro aparece perto do campo?

O auxiliar existente acessibilidadeFormulario escuta o evento invalid. Quando um campo é inválido, ele acrescenta uma mensagem de texto ao lado desse campo, marca aria-invalid e usa aria-describedby para relacionar campo e mensagem.

Assim, o erro continua disponível mesmo depois que o balão do navegador fecha. Quando o valor é corrigido e fica válido, o auxiliar remove sua mensagem e as marcações de erro. O navegador continua responsável por indicar o primeiro campo inválido durante a tentativa de envio.

Captura antes da propagação: por que a ordem importa?

formulario.addEventListener('input', aoAlterar, true);
formulario.addEventListener('change', aoAlterar, true);

O true pede para tratar esses eventos na fase de captura. Primeiro a nova regra atualiza a validade; depois, na fase de propagação, o auxiliar de acessibilidade lê o resultado. Isso evita que uma mensagem antiga permaneça depois de corrigir o texto.

O evento invalid não se propaga da mesma forma que input. O auxiliar de acessibilidade já o escuta em captura para atender aos campos do formulário. A #20 complementa essa estrutura existente.

Botão desabilitado e guarda no código

disabled comunica que o botão está indisponível e bloqueia seu uso normal. A função de envio também verifica o estado antes de chamar o código que grava a tarefa:

if (enviando || carregandoProjetos || erroProjetos) return;
if (!(evento.currentTarget as HTMLFormElement).reportValidity()) return;

O primeiro if impede executar o envio enquanto ele já está acontecendo ou sem ter os projetos disponíveis. O segundo pede a conferência nativa com reportValidity(); se houver campo inválido, a função encerra ali.

Durante a gravação, o botão mostra Salvando... e permanece desabilitado. A guarda no código dá proteção adicional contra chamadas repetidas; o cadastro também mantém seu controle de tarefa já criada para não repetir um POST depois do sucesso.

Erro de preenchimento e falha da API são diferentes

SituaçãoComo tratamos
Título vazio ou só com espaçosImpedir o envio e mostrar a mensagem junto do campo. A pessoa corrige o conteúdo.
Os projetos ainda estão carregando ou falharamNão enviar com as opções indisponíveis. Mostrar a situação de carregamento ou erro.
A API falha ao salvar dados válidosManter os dados e mostrar a falha de gravação. Depois que o envio termina, permitir uma nova tentativa.

A mensagem de uma tentativa anterior de salvar não é, por si só, motivo para bloquear a próxima. Por isso, a guarda do componente verifica erroProjetos, mas não bloqueia o envio apenas porque a prop erro ainda contém a falha anterior da API.

Como chegar a esta parte: abra src/lib/utils/validarObrigatorios.ts para ler a regra. Depois procure use:validarObrigatorios na página de nova tarefa e em FormularioTarefa.svelte. Compare com use:acessibilidadeFormulario para separar quem confere o valor de quem apresenta o erro.

10Issue #21: entender e operar o formulário

Uma pessoa precisa reconhecer os campos, chegar até eles por teclado e compreender o erro. Só deixar uma borda vermelha não explica qual é o problema.

<label for="tarefa-titulo">Título (obrigatório)</label>
<input id="tarefa-titulo" type="text" required />

for aponta para o id do campo. O label dá um nome persistente ao controle. Placeholder sozinho não substitui esse nome.

RecursoO que comunica
aria-invalid="true"O campo está marcado como inválido.
aria-describedby="..."Associa o campo ao texto explicativo por ID.
role="alert"Marca uma mensagem importante, como o erro apresentado.
aria-busyInforma que aquela região está em processamento.
:focus-visibleMostra onde está o foco ao usar teclado.

O auxiliar do grupo

acessibilidadeFormulario acompanha eventos de validação nos formulários de tarefa. Ele cria uma mensagem ao lado do campo, associa essa mensagem por ARIA e a retira quando o campo fica válido. Sua limpeza também remove os ouvintes de eventos quando o formulário sai da tela.

Esse auxiliar não chama focus(). Nos formulários de tarefa, o foco no primeiro campo inválido vem do comportamento de validação do navegador. Nos projetos, o componente constrói seus próprios erros e associações ARIA.

Uma conferência por teclado

  1. Use Tab e Shift+Tab para percorrer os campos, o botão e o cancelamento.
  2. Confira se o foco é visível e segue uma ordem compreensível.
  3. Preencha um seletor com as setas e tente enviar pelo teclado.
  4. Deixe um campo obrigatório inválido e leia a mensagem escrita junto dele.
  5. Corrija o valor e confira se a mensagem deixa de indicar um erro antigo.

Como chegar: abra src/lib/utils/acessibilidadeFormulario.ts e procure mostrar, limpar e os eventos invalid, input e change.

11Issue #22: cadastro e edição de projetos

Projeto e tarefa têm contratos diferentes. No formulário de projeto a pessoa preenche nome, descricao e disciplina. A API gera o id; a página de cadastro acrescenta criadoEm.

Cadastro em /projetos/novo

A página prepara os três campos vazios e passa ao componente FormularioProjeto. Sua função de salvar recebe os campos, acrescenta a data local e chama a API.

const projeto = await criarProjeto({
  ...dados,
  criadoEm: hojeLocal()
});
return `/projetos/${encodeURIComponent(projeto.id)}`;

O componente aguarda esse retorno e usa o endereço para continuar. hojeLocal() monta ano, mês e dia no fuso do computador. Isso evita usar sem querer o dia seguinte de UTC ao cadastrar à noite no Brasil.

Edição em /projetos/3/editar

A página carrega o projeto e passa seus valores atuais ao mesmo componente. Ao salvar, compara os campos com o registro carregado e monta alteracoes apenas com o que mudou.

if (dados.nome !== atual.nome) {
  alteracoes.nome = dados.nome;
}
if (Object.keys(alteracoes).length > 0) {
  await atualizarProjeto(atual.id, alteracoes);
}

O ID e a data de criação permanecem os do registro original. Se nada mudar, essa página não envia PATCH. O bloco {#key projeto.id} recria o formulário quando outro projeto é carregado; por isso, a cópia inicial dos campos pode ser feita uma vez.

Validação e envio têm uma implementação própria

FormularioProjeto usa novalidate, retira espaços das pontas e cria mensagens para campos vazios em sua função validar(). Seus controles continuam com required, mas novalidate desativa a verificação automática dessas regras no envio: validar() confere os três campos. Já preventDefault() impede o envio tradicional do formulário.

O fieldset é bloqueado enquanto salvando é verdadeiro. A guarda salvando || salvo evita um segundo envio durante a operação ou depois do sucesso. Se a API falhar, os dados são mantidos. Se a gravação der certo mas a navegação falhar, aparece um link “Continuar”.

Não misture as duas estratégias: os formulários de tarefa preservam a validação nativa e a complementam; o formulário de projeto valida por código com novalidate. ARIA comunica os resultados, mas não é uma função de validação.

Como chegar: abra as duas páginas em src/routes/projetos, o componente FormularioProjeto.svelte e src/lib/utils/projetos.ts.

15Perguntas que a professora pode fazer

Estas são possibilidades de estudo, não uma previsão da prova. Treine explicar o motivo e apontar um exemplo no código. No final há um simulado de múltipla escolha para você responder.

1. Por que /tarefas/nova não abre o detalhe de uma tarefa chamada “nova”?

Porque existe uma rota fixa em tarefas/nova/+page.svelte. O SvelteKit dá prioridade à rota fixa sobre tarefas/[id]/+page.svelte.

2. De onde vem o projeto que aparece selecionado?

Do parâmetro projetoId na consulta da URL, enviado pelo link da página do projeto. O código lê essa sugestão e confere se ela corresponde a um projeto existente nas opções da API.

3. Qual é a diferença entre GET e POST nesta tela?

GET lê os projetos. POST envia os dados para criar a tarefa. A requisição de criação leva um corpo JSON.

4. Por que não enviamos um id junto com os campos?

O ID é gerado pela API. O tipo NovaTarefa usa os campos de Tarefa sem id, deixando isso claro enquanto programamos.

5. O que aconteceria se voltássemos para a lista antes de esperar a API?

A pessoa poderia ver a lista antes da gravação terminar ou sair do formulário sem perceber uma falha. A ordem correta é confirmar a criação e depois navegar.

6. O que bind:value faz quando você digita um título?

Atualiza o estado ligado ao campo. A ligação também funciona no outro sentido: quando o código altera esse estado, o valor mostrado no campo acompanha a mudança.

7. Para mudar só a prioridade, uso criarTarefa ou atualizarTarefa?

Uso atualizarTarefa, passando o ID do registro e um objeto como { prioridade: 'alta' }. O pedido usa PATCH. criarTarefa usa POST para acrescentar uma nova tarefa.

8. Qual é a diferença entre Omit e Partial nesses tipos?

Omit<Tarefa, 'id'> retira o ID do tipo de criação. Partial<NovaTarefa> torna opcionais os campos da atualização, permitindo enviar apenas aqueles que devem mudar.

9. No cadastro de um projeto, quem fornece criadoEm?

O código que chama criarProjeto fornece esse campo no objeto NovoProjeto. A função envia os dados recebidos; a API gera o ID, sem inventar a data de criação.

10. Onde vão o ID e os novos valores em uma atualização?

O ID identifica o registro na URL, como /tarefas/2. Os valores que devem mudar vão no corpo JSON do PATCH. A função codifica o ID com encodeURIComponent ao montar o endereço.

11. Promise<Projeto> quer dizer que já tenho um projeto pronto?

Não. É um resultado que pode chegar depois. Ao usar await, esperamos a operação; se ela tiver sucesso, recebemos o projeto. Se falhar, tratamos o erro no catch.

12. Por que todas as funções usam requisitar?

Porque a chamada de rede, a leitura do JSON e a checagem de sucesso são passos comuns. O auxiliar recebe o caminho e opções RequestInit, evitando repetir esses passos em cada função.

13. Por que um título só com espaços precisa de outra regra além de required?

Porque ele contém caracteres, embora não tenha texto útil. A nova regra confere se ainda sobra algum conteúdo depois de trim(). Se não sobrar, marca um erro personalizado.

14. O que significa chamar setCustomValidity com uma string vazia?

Significa limpar o erro personalizado dessa regra. As outras verificações nativas, como required, continuam valendo. Isso permite que um campo corrigido volte a ser considerado válido.

15. Quem mostra o erro junto do campo?

O auxiliar acessibilidadeFormulario, já entregue pelo grupo. Ele usa o evento invalid, insere a mensagem em texto e relaciona a mensagem ao campo com atributos ARIA. A nova action fornece a regra adicional de validade para texto só com espaços.

16. Por que a nova regra escuta input e change em captura?

Para atualizar a validade antes que o auxiliar de acessibilidade, na fase de propagação desses eventos, leia o resultado. Assim, corrigir o texto também atualiza a mensagem na ordem certa.

17. Se o botão já está disabled, para que verificar enviando dentro da função?

O botão desabilitado bloqueia sua interação normal e comunica o estado. A função também verifica se há envio em andamento para evitar executar novamente o código de gravação. São duas proteções trabalhando juntas.

18. Uma mensagem de falha da API deve impedir a próxima tentativa de salvar?

Não. Depois que a tentativa termina, a pessoa precisa poder tentar outra vez. O código bloqueia durante o envio e quando os projetos estão indisponíveis; ele não usa a mensagem de uma falha anterior de gravação como trava permanente.

Mais perguntas para a apresentação

Qual é a diferença entre Svelte, SvelteKit e TypeScript?

Svelte organiza componentes e reatividade. O projeto usa SvelteKit para a estrutura de páginas e a navegação por arquivos. TypeScript descreve os tipos e ajuda a detectar incompatibilidades durante o desenvolvimento; seus tipos não validam sozinhos a resposta recebida da API.

Como o componente avisa à página que deve salvar?

A página passa a função salvar em onenviar. O componente chama onenviar(dados). Esse callback liga o formulário à decisão de gravar na API, sem obrigar o componente a conhecer a rota de destino.

O formulário de tarefa está mesmo reaproveitado nas duas telas?

Na base consultada, FormularioTarefa é usado na edição. A tela de nova tarefa tem formulário próprio. O componente foi preparado para reutilização, mas a integração nas duas telas ainda é uma melhoria possível. Em projetos, FormularioProjeto é usado de fato nos dois fluxos.

Por que buscar os dados antes de editar?

A pessoa precisa ver o estado atual do registro e alterar o mesmo ID. GET carrega a tarefa; PATCH grava as alterações. Abrir a edição sem os valores atuais pode levar a sobrescrever campos sem perceber.

Por que não basta deixar o erro vermelho?

Cor sozinha não informa qual campo está errado nem atende quem não a distingue. O projeto usa texto junto ao campo, labels e associações ARIA, além de foco visível e controles operáveis por teclado.

O projeto novo e o editado mudam a data de criação do mesmo jeito?

Não. O cadastro acrescenta criadoEm com hojeLocal(). A edição preserva criadoEm e id e envia apenas os campos alterados. A data de criação não deve virar a data de cada edição.

Todos os formulários validam do mesmo jeito?

Não. Tarefas complementam a validação nativa com a regra de espaços e o auxiliar de acessibilidade. FormularioProjeto usa novalidate e verifica seus campos em validar(). É preciso explicar cada implementação como ela realmente é.

Se fosse melhorar a solução, por onde começaria?

Uma melhoria ligada ao próprio pedido é integrar FormularioTarefa também à nova tarefa, preservando a seleção de projeto, as mensagens e os testes. Outra é revisar os slides e o README para que descrevam o código atual. Isso é uma proposta, não algo feito por este guia.
